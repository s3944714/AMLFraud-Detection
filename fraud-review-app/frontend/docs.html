Documentation

Fraud Case Review is the batch-scored case-review workbench half of a two-part portfolio project. This page covers how it works, its API, and the file contract it depends on.

Overview

This application never runs a model, computes SHAP values, or builds an entity graph itself. It reads three flat files — produced by a separate offline pipeline (the IEEE‑CIS Fraud Detection dataset, scored by a LightGBM classifier) — and serves them through a small JSON API to this frontend. That's a deliberate architectural choice, not a limitation: it mirrors how a real fraud-ops system actually runs, where scoring happens as a batch job and a review tool serves that job's output, rather than scoring transactions live on every page load.

The backend is FastAPI; the frontend is hand-written HTML, CSS (Tailwind, loaded via CDN, no build step), and JavaScript with a single external dependency (D3.js, for the entity-link diagram in the case detail panel).

How scoring works

Risk score

Each transaction's risk_score comes from a LightGBM classifier trained on a strict time-based train/test split — not a random split, since fraud patterns and feature distributions drift over time in this dataset, and a random split would let future transactions leak into training. The model is evaluated on precision-recall AUC and recall-at-alert-budget rather than accuracy, since accuracy is close to meaningless at this dataset's roughly 3.5% fraud rate: a model that flags nothing at all still scores over 96% accuracy.

Reason codes

Each case's top_reason and the fuller SHAP breakdown in its detail panel come from SHAP (TreeExplainer), identifying which features pushed that specific transaction's score up or down. Most of this dataset's columns (V1–V339, C1–C14, D1–D15, most id_* columns) are anonymized, Vesta‑engineered features that Kaggle never discloses the meaning of. Reason codes for those columns are phrased honestly — "an anonymized engineered feature," with its value and direction — rather than inventing plausible-sounding business meaning that isn't actually known. Named columns with real-world meaning (transaction amount, product category, card network, email domain) get a genuine plain-language description.

Ring detection

A "ring" here means a cluster of transactions linked by a shared card+address combination, device, or email domain, found via connected-components on an entity-link graph, where the cluster's fraud rate is at least double the dataset baseline. This is unsupervised structure-finding, not a verified-fraud-ring detector: a flagged cluster is a lead worth an investigator's attention, not a conviction. Shared attributes can also arise from mundane reasons (a shared household, a shared office).

API reference

All endpoints return JSON and require no authentication (this is a single-tenant review tool, not a multi-user system).

GET /api/cases

List cases from the queue, filtered, sorted by risk score (highest first), and paginated.

Parameter Type Default Description

cluster_onlybooleanfalseOnly return cases linked to a candidate ring

offsetint, ≥ 00Rows to skip before the page starts

GET /api/budget-simulation

Recall achieved at a given review budget, reviewing by risk-score order versus a seeded random baseline of the same size.

Query parameters for GET /api/budget-simulation
Parameter Type Default Description
budget_pctfloat, 0–1requiredFraction of the queue a review team can cover

If the loaded data includes an isFraud column, this reports true recall. The real exported pipeline data deliberately omits it — a production deployment wouldn't have ground truth at scoring time either — so in that case this falls back to a documented proxy: the fraction of candidate-ring-linked transactions captured, which correlates strongly with fraud but isn't a confirmed label. The response's metric_name and note fields always say plainly which one you're looking at. 

GET /api/budget-simulation?budget_pct=0.1

{
  "budget_pct": 0.1,
  "n_transactions": 5906,
  "n_reviewed": 591,
  "metric_name": "candidate_ring_capture_rate",
  "is_ground_truth_available": false,
  "model_metric": 0.42,
  "random_metric": 0.09,
  "model_count": 187,
  "random_count": 41,
  "note": "No isFraud ground truth in the loaded data, so this is a PROXY metric: ..."
}

File contract

The backend reads three CSVs and an optional metadata file from a data directory, set via the DATA_DIR environment variable (defaults to the bundled synthetic sample in data/sample/).

scored_transactions.csv — required

TransactionAmtFloat

cluster_idNullable — set only for candidate-ring members

Missing entirely means the app still runs; case detail pages just show no SHAP breakdown.

metadata.json — optional

A dict with at least a pr_auc key, surfaced via /api/summary. Missing means that field is null.

Limitations

This is a portfolio and research project built on public competition data, not a production AML system. A real deployment would need AUSTRAC-compliant model documentation, ongoing model risk management, formal validation, and case-management workflows (escalation paths, audit trails, SAR/TTR filing) that this project doesn't attempt to replicate. Candidate rings are unsupervised leads, not confirmed fraud. Where ground truth isn't available, the budget simulator says so explicitly rather than presenting a proxy metric as if it were verified recall.
